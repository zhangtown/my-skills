# 投标文件全自动编写与排版 (Tender Bid Writer)

## 这个技能做什么

把"招标文件 + 一份只有 1~2 级标题和页数预算的大纲"变成一份**内容成稿、排版到位**的中文
技术投标文件 `.docx`。在无任何参考资料的情况下，从需求出发自己写满内容、生成图表、套用
招投标通行的 Word 排版规范（自动目录、五级标题、分章图表编号、正文页码；一律不做封面）。

职责分工：**你负责写内容**（理解需求、扩写章节、设计表格、规划配图），
**`scripts/build_docx.py` 负责排版**（字体字号、行距缩进、编号、目录域、页码，全部确定性自动完成）。
你只需把内容填进一个 JSON，引擎产出格式完全合规的文档。这样既保证内容质量，又保证排版零失误。

## 触发后先确认的关键信息

> **默认只编写技术标**：本技能只产出**技术标**，不涉及商务标/报价标。**不要**再询问"是否只写
> 技术标""要不要写商务标"之类的问题，直接按技术标编写。

**每次触发后，用 AskUserQuestion 的多题表单把该问的一次性问完——能选的给选项、要填的用输入
（"其他"里填），多题一起呈现（客户端会分页 1/N、2/N…），用户一次提交后即开跑。切勿让用户手填一整张
Markdown 大表格。**

一次 AskUserQuestion 最多 4 题，用**一次调用**问下面 4 项决策：

1. **明标/暗标**（选项）：`暗标（默认）` / `明标`。含义见下方专条。
2. **总页数**（直接让用户输入，不给下拉）：在"其他"里填"__页"。直接决定字数预算。
3. **是否参照参考文件**（选项）：`否（默认）` / `是`。让指定章节参照往期标书/技术方案的某节编写。
4. **其他内容特殊要求**（无就选`无`、有就在"其他"里填）：**内容层面**的要求（要写/不写什么、口径侧重、
   必须体现的点），会被**理解消化后落到规划与生成执行**，不是记下就算。

> **文件一律由用户显式提供、绝不自动扫描或猜测**：招标文件、投标大纲（`outline.json`）、参考文件
> **必须等用户主动给出**（拖文件进来、贴路径、或明确指到某个文件夹里的某个文件）。**严禁**主动去
> 扫描桌面/已连接文件夹、列举候选、或替用户挑文件——用户没给文件，就不许开始找文件、更不许开始跑。
> 只有当用户明确说"就用这个文件夹里的"时，才在该文件夹内定位；其余情况一律等用户给。

用户提交决策表单后，**先按下面把文件收齐、拿到手再往下走**：
- **第 3 项选"否"** → 请用户提供 ①招标文件 ②投标大纲，**收到文件后**进入 规划→生成→检查→出稿，
  全程只在 plan 冻结、一致性检查两个既定闸口停。
- **第 3 项选"是"** → 请用户提供 ①招标文件 ②投标大纲 ③参考文件，**收齐后**再做**唯一的一次追加交互**，
  逐条收 `【本文件章节 标题】参考【参考章节 标题】`，两种方式任选（见下文「参考资料」一节）：
  · **甲·按脚本编号**：跑 `python scripts/references.py pair --outline <outline.json> --refs <参考文件>`
    打印两份带层级编号 `1.1.1` 的目录（drill 到每级、原样贴出，严禁手打/缩写），用户照编号绑；
  · **乙·按标题（用户说"我开原文件绑"时走这条）**：不必列整棵树，用户直接给标题原文，
    重名用 `父.子` 消歧；每条当场用 `find_section` 解析、回显匹配到的参考节+首句供确认。
  **切勿让用户照 Word 显示的自动编号绑**（那些号不在正文里、引擎按位置现编，可能整体错位）。

无论哪种情况，**用户没把文件给到之前不得开工**——不扫描、不猜、不列候选。

排版样式、封面、参考章节样式**一律不问、走默认**（详见下方两条专条）。

> **排版样式一律走默认、不提问**：正文默认宋体小四 +1.5 倍行距、A4、自动目录、五级标题、分章图表
> 编号、正文页码、不做封面。**不要**再就排版样式（字号/行距/页边距/目录级别等）向用户提任何问题。
> 招标文件若明确规定了不同排版，改 `scripts/format_config.json` 对应字段即可，无需询问用户。
>
> **参照参考文件时的样式一律不问**：参考章节的标题/列表/正文/题注格式由引擎按本投标文件总体规范
> 自动重排、天然一致。**不要**再询问"参考章节要不要跟总体格式一致""参考有没有特殊样式要求"之类——
> **样式信息全部不提问**。

> **明标/暗标（最高优先级）**：
> - **明标**：允许出现投标人名称、承揽项目、人员等信息。
> - **暗标**（默认）：全文严禁出现任何可识别投标人身份的信息——公司/单位名称、承揽过的项目名、
>   人员姓名与职务、带 logo 或单位标识的图，一句话即**不能有任何看得出是哪家公司的蛛丝马迹**；
>   也不得整段介绍投标人的组织架构、资质、业绩经验与贡献。确需按大纲/采购需求做介绍时也必须
>   完全匿名（用「投标人」「项目实施团队」「本方案」等泛称）。暗标经 `run_all.py` 的
>   `--blind-bid`（或交互选择）落到 `plan.meta.blind_bid`，贯穿生成提示词、界面图 logo 清除、
>   一致性检查的暗标查漏（扫描疑似公司名后缀并告警，人名/logo 仍需人工复核）。
>
> **一律不做封面**：无论明标暗标都不编制封面，编写前也不询问封面所需信息。

> **永久规则（不可违反）**：用户给出的大纲结构——每一级标题的**文本、层级、顺序、父子关系**
> ——一律不改、不删、不合并、不重排。只能在用户已有的章节内**细化更深一层的子标题、填充内容**。
> 规划与生成脚本都按节点 id 回填，从机制上保证不动结构。

> **永久规则 · 数值指标克制（全局强制）**：除招标文件/采购需求中明确给定、并已收入数据字典的
> 数值指标外，各章节正文**一律不得自行编造任何数值型指标或统计数字**（百分比、倍数、次数、时长、
> 金额、数量、占比等，如"虚警占70%""平均点击15次以上"这类凭空数字）。确需体现程度/规模/对比时
> 改用模糊定性表达（"占比偏高""大幅下降""操作繁琐需多次切换"）。唯一例外：参考资料原文中确有
> 出处的指标可沿用（此时以参考为准）。该规则已内置进生成提示词，对所有章节生效。

> **产物落盘位置**：一键编排（`run_all.py`）未显式指定 `--workdir` 时，`plan.json`/`content.json`/
> 成稿 `.docx`/界面图默认都落在**投标大纲所在目录**，与大纲同处一处，便于交付与归档。
> 手动分步或模式 B 直填时，也应把成稿 `.docx` 保存到大纲同目录。

## 模型与环境

```bash
pip install python-docx Pillow --break-system-packages
export DEEPSEEK_API_KEY=sk-xxx           # Windows(PowerShell): $env:DEEPSEEK_API_KEY="sk-xxx"
# 默认：规划 deepseek-v4-pro，写作 deepseek-v4-flash（可用环境变量覆盖）
export DEEPSEEK_PLAN_MODEL=deepseek-v4-pro
export DEEPSEEK_WRITE_MODEL=deepseek-v4-flash
```
两种模式：**A 自动逐叶生成**（推荐，主线）；**B 手写直填 `content.json`**（短标书/小修改，跳过阶段一二）。

**一键编排**：outline.json 就绪（转写已校验）后，可用 `run_all.py` 串起阶段一到三，
在 plan 冻结与一致性检查两处暂停等人工确认（`--yes` 跳过闸口，不建议正式使用）：
```bash
python scripts/run_all.py --outline outline.json --pages 80 \
    --scoring scoring.txt --requirements req.txt \
    --font-size 小四 --line-spacing 1.5倍 --docx 投标文件.docx
```
中断后重跑同一命令即可（generate 自动断点续上）。阶段四验证仍须单独执行。

## 可选 · 参考资料（编写前必问是否参照）

除招标文件与大纲外，用户若还有参考资料（往期标书、技术方案等），可让**指定章节参考
指定资料的某一节来编写**。**是否参照即首张收集表的第 ③ 项**（是/否，默认否）；选"是"时，
用户提交表后进入唯一的一次追加交互：列出带层级编号的两份目录、收齐绑定后即开跑。

**绑定的定位主键有两条等效路径，都由 `find_section` 解析——按用户从哪儿看章节来选**：

- **路径甲 · 按脚本编号绑（用户看 `pair`/`show` 输出）**：脚本给每个标题标了同源层级编号
  `1 / 1.1 / 1.1.1`，用户按 **`【本文件章节号 标题】参考【参考章节号 标题】`** 输入，
  例如 **`【2.1 需求分析】参考【3.1 需求分析】`**，`ref.section` 写参考侧层级编号（如 `"3.1"`）。
- **路径乙 · 按标题绑（用户直接打开原始文件对照，推荐给"我看原文件绑"的场景）**：
  用户看到的标题文字就是锚点，`ref.section` 直接写**标题原文**（如 `"已有工作基础"`）；
  重名时写 **`父.子` 路径**消歧（如 `"已有工作基础.平台架构"`）。`find_section` 按标题
  精确/包含匹配，天然与用户屏幕所见一致。

> ⚠️ **不要让用户照 Word 里显示的编号绑。** 多数参考文件的"3.2""4.2"是 **Word 自动编号、
> 不写在正文里**，引擎读不到、只能按位置**现编**一套 `_hier_numbers`（`show` 展示号 = `find_section`
> 解析号，完全同源）。脚本编号与 Word 显示号**通常一致但可能整体错位**（如某个未编号的抬头标题
> 会让其后全体差一位）。所以：**要么用路径甲、绑 `show` 打出来的号；要么用路径乙、绑标题原文——
> 唯独不能凭 Word 界面上看到的号绑。** 拿不准时一律用路径乙（标题最稳）。
>
> **用户明说"我直接打开原始文件绑定"时**：走路径乙，**不必**先跑 `pair` 列整棵树，直接一问一答
> 逐条收 `【投标标题】参考【参考标题】`；每收一条就用 `find_section` 解析、**回显匹配到的参考节
> 标题+正文首句**给用户确认；标题重名解析不唯一时，请用户补 `父.子`。

绑定既可在对话里逐条口述、由你把 `ref` 字段直接写进 outline.json，也可用 `--references` 走
交互式命令行绑定（节号处填 `文件号:层级号`，如 `0.1 1:3.1`）。`section` 也仍兼容原生编号、
纯标题、点号路径等旧写法作**兜底**；均对不上时不静默退回纯生成，而应在审查环节暴露（见常见坑）。
不提供参考资料时该功能完全不介入（未绑定章节纯大模型生成，零回归）。

> **对话式逐条绑定的问答节奏（用户选择"逐章指定参考绑定"后必须遵守）**：
> 一次只收一对绑定，一问一答，不要让用户一口气把所有绑定列完。
> 0. **收第一对绑定前，必须先把两份大纲都罗列出来供用户对照定位——只能用脚本打印、严禁自己眼看手打**：
>    运行 **`python scripts/references.py pair --outline <outline.json> --refs <参考文件,逗号分隔>`**，
>    它会一次性打印**①本投标文件大纲**与**②每个参考文件的章节大纲**，两者都带同源层级编号
>    `1 / 1.1 / 1.1.1 / …` 并 **drill 到每一级叶子**（投标侧走 `_bid_hier`，参考侧走 `_hier_numbers`）。
>    **把脚本原样输出照实贴给用户，不得删节、合并（如把 `4.1~4.4` 缩写）、跳级或漏掉任何子节**——
>    手工转录必然出错，这正是之前列错的根因。编号是绑定定位主键，缺号用户就没法用
>    `【号 标题】参考【号 标题】` 精确指节。（只需看参考侧可单独用 `show`；只需看投标侧可单独用 `outline`。）
>    贴完再进入下面第 1 步。
> 1. 先提示：**"请输入第一对绑定关系"**，然后**停下等用户回车输入**。
> 2. 用户输入后，**立即回显你解析出的『参照绑定设置』**（本次绑定的大纲章节 → 参考文件与节、
>    参照程度 mode），供用户确认。
> 3. 接着提示：**"请输入第二对绑定关系"**，再停下等待；如此"第三对、第四对……"逐条进行。
> 4. 当你提示"请输入第 N 对绑定关系"后，用户回复 **"无"或"已完成"**，即视为绑定结束，
>    汇总全部绑定、把 `ref` 字段写入 outline.json，进入后续环节。
> 每对绑定都要当场确认参照程度（①改写借鉴／②保子标题优化／③完整照抄），未指明默认①。

**三种参照程度（每条绑定单选，写入节点 `ref.mode`）**：
- **① 改写借鉴 `adapt`**（默认）：**以参考章节内容为本节主干**，其要点/方案/细节都要吸收展开，
  由模型改写重述成贴合本项目的内容（保留实质信息、统一术语指标、去公司痕迹），而非仅当灵感点缀。
  强弱按绑定精度自动分流：**用户手动精准绑到某节（`auto=False`）用"以参考为主"强措辞；
  相似度自动匹配或从父章继承来的绑定（`auto=True`）退回"仅借鉴要点"弱措辞**，避免把未必对口的
  素材当主干、放大错配。adapt 的注入素材在进提示词前也会跑一遍字典指标就近替换（与③一致的确定性
  兜底），不再单靠模型自觉。
- **② 保子标题·优化 `keep_headings`**：保持参考章节下**所有子标题原样、顺序不变**，只对正文
  做轻度润色。**仅能绑定到叶子节点**（避免与大纲结构冲突）。
- **③ 完整照抄 `verbatim`**：把参考章节下全部内容按块直接重建、**不调用大模型**；与关键指标
  冲突处**自动以数据字典的值替换**并在日志记录。

无论哪种模式，两条硬约束始终生效：**①各级标题/列表标题/正文/题注等所有排版一律套本投标文件
的总体排版格式，绝不保留参考文件原格式**（引擎按投标规范渲染重建的 h 块，与其余章节完全一致）；
**②编入的内容不得与关键指标、暗标要求冲突**——数值指标/产品选型/项目背景一律以数据字典为准，
暗标下参考带来的公司/项目名称同样不得写入。继承的绑定强制降为 `adapt`（②③只在自身绑定的叶子生效）。

> **参考章节的排版自动统一，无需询问**：参考文件编入的章节，其标题/列表/正文/题注格式由引擎
> 按本投标文件的总体排版规范自动重排，天然与其它章节一致。**不要**再就"参考章节要不要跟总体
> 格式保持一致"向用户确认——这是既定行为，直接执行。

`ref` 字段（写进 outline 节点）：`{"file": 路径, "section": "1.1.1"或标题或null, "mode":
"adapt"|"keep_headings"|"verbatim", "exclude": false}`。**`section` 首选写 `show` 输出里的
层级编号（`"3.1"`）**——唯一、可复现、无需消歧，是推荐主键。以下写法仍作**兜底**保留：
纯标题（`"关键技术"`）、点号路径 `"祖先.…目标"`（如 `"已有工作基础.关键技术"`，用于重名标题
按祖先消歧）、原生编号。用层级编号绑定时天生避开重名问题，不必再写点号路径。**一个节点也可绑定多份参考**：把
`ref` 写成绑定对象的**数组**（如 `[{"file":..,"section":"建设情况"}, {"file":..,"section":
"推广应用"}]`），生成期会把各节整节取出、带出处小标后合并注入同一叶子，仍走"以参考为主"强绑定。

> **精准绑定的叶子永不被拆分、整节注入**：凡带自身 `ref`（单条或多条）的叶子，规划阶段的
> "大叶子拆分"一律跳过它——因为拆分会把 `ref` 留在父节点、子叶不带 ref，生成期只能按"继承·
> 弱借鉴"处理，逼着子叶从窄切片扩写大字数，导致成稿与参考**相差过大**。整叶保留后由
> generate 的强绑定分支照参考写；预算过大时由 generate 的 `--chunk` 分块兜底（每块仍带同一
> 参考）。同时精准绑定按 `OWN_CAP_CHARS`（默认 12000 字）整节注入，不再截到 3000 字丢内容。

命令行用法（可选，交互绑定）：
```bash
python scripts/run_all.py --outline outline.json --pages 80 \
    --scoring scoring.txt --requirements req.txt \
    --references 参考A.md,参考B.docx --docx 投标文件.docx
```
- **推荐格式 md / 规范 docx（用了标题样式）优先，pdf 可靠性最低、降级需在预览中逐节确认**。
- **继承可否决**：某章绑定后其全部子叶自动继承（继承一律 `adapt`）；绑定非叶子会回显子叶清单，
  可逐个排除；某子叶在参考资料里匹配不到内容（相似度过低）时自动退回纯大模型生成。
- **排版前审查闸口**：`check_consistency.py` 会列出「哪些章节以何种模式参考了哪份资料的哪一节、
  照抄模式按字典替换了几处指标」，并对被参考章节里出现、但不在数据字典里的**疑似指标数字**告警、
  对**同一节被多章引用**提示重复，供人工核对（全部为警告、不阻断）。
- 单独解析预览参考文件的章节树：`python scripts/references.py show --refs 参考A.md`。
- **参考文件结构体检（绑定前先跑一遍）**：`python scripts/ref_healthcheck.py 参考A.docx`。
  它一次性给出①解析器实际认出的层级章节树，②**疑似漏标题**清单——即源文件里那些
  "看着像子标题、却没套 Word「标题N」样式、也没大纲级别"的短行（会被当正文吞进上一节、
  无法用编号单独绑定）。若用户要绑的正是这类节，提示其在源 docx 里给该行套上标题样式后重跑。
  加 `--raw` 逐段打印 样式/大纲级别/列表编号/加粗（配 `--kw 关键词` 聚焦），用于排查解析异常。
  **重要**：当用户反映"参考目录某节的子标题没显示出来"时，先跑本体检确认到底是解析问题
  还是源文件没套标题样式——不要凭印象改解析逻辑。

## 四阶段工作流

### 阶段一 · 规划（v4-pro，产出 plan.json）
1. 读招标文件，**输入只需采购需求 + 评分标准**。生成 `outline.json`（标题树；用户备注放 `note`）：
   - 大纲源文件是 .docx 时**必须用脚本确定性提取，禁止手工/模型转写**：
     ```bash
     python scripts/outline_from_docx.py 大纲.docx -o outline.json
     ```
   - 只有大纲以纯文本/图片给出时才允许转写；转写后必须把标题树打印给用户逐级确认。
   - 有源 .docx 时，进入规划前**必须过校验**（返回码非 0 不得继续）：
     ```bash
     python scripts/outline_from_docx.py 大纲.docx --check outline.json
     ```
   - **绝对禁止按评分表重排大纲**。评分因素的名称与归属经常和章节结构不一致
     （如评分表把"项目执行整体思路"列在"项目需求分析"因素之下），章节结构一律以大纲文件
     为准；"分数→章节"由规划阶段做**语义映射**，绝不为对齐评分表而调整任何标题的
     文本、层级、顺序或归属。
2. 跑规划脚本——`deepseek-v4-pro` 负责"理解"，Python 负责"算页数"：
   ```bash
   python scripts/plan.py --outline outline.json --pages 80 --out plan.json \
       --scoring scoring.txt --requirements req.txt \
       --font-size 小四 --line-spacing 1.5倍               # 离线测试加 --mock
   ```
   每页字数按正文样式查表（小四+1.5倍=883 字/页，默认）；特殊排版用
   `--words-per-page N` 直接指定。
   大纲叶子多时自动**分批调用**（默认 25 叶/批，`--batch` 可调），并做**规划覆盖率校验**：
   缺 brief/关键词的叶子会先自动补漏一次，仍缺的以警告显式列出——**看到该警告必须处理，
   不得带着无约束的叶子进入生成**。它产出 `plan.json`（结构见 `references/plan_schema.md`）：
   - **数据字典** `dictionary`：指标标准值、统一术语+禁用同义词、信创选型一次定死（全篇唯一事实源）。
   - **大纲树** `outline`：镜像用户结构，给每个**叶子**配 `brief`(写什么内容)/`aspects`(从哪些方面
     逐一展开)/`min_words`(至少多少字)/`must_keywords`/`weight`/`template`，并按评分逻辑算出每个叶子的
     `page_budget`/`word_budget`。叶子若带用户 `note` 备注，据此细化 `aspects`/`min_words`；
     生成时实际字数下限取 `max(word_budget, min_words)`。
   - **页数逻辑**：技术总分 A → 每分页数 B=总页/A → 章节页=章节分×B →
     一级章节**兜底 10 页**（不足抬满后其余等比缩放，保持总页数）→ 章内按 weight 分到叶子。
   - **大叶子拆分**：分页后 `word_budget` 超过 `--split-threshold`（默认 6000 字）的叶子，
     再调 v4-pro 在其**内部**细化 2~5 个下一级子标题，变成多个小叶子各自独立生成——
     从机制上消除超长叶子分块续写的重号/衔接风险。子叶权重按父叶等比缩放（章内页数份额不变），
     父叶关键词全部分配到子叶后重算页数/字数。已到第 5 级无法再细化的叶子回退 generate 分块续写。
     **例外：带自身 `ref` 参考绑定（单条或多条）的叶子一律不拆**，整叶保留以保参考保真（见「参考资料」一节）。
3. **把 `plan.summary` 给用户审核**（尤其数据字典与各章页数），**冻结后再生成**。
   > **数据字典必须逐条对照采购需求核验（最易漏、后果最重）**：规划阶段已把字典抽取拆成
   > **独立调用**（不再与叶子回填抢注意力/token），并从采购需求/评分标准里**确定性捞取"疑似指标
   > 行"**喂模型逐条甄别；字典为空或明显偏薄时**自动定向补抽一次并 `[警告]` 告警**。但审核时仍须
   > 把字典与招标文件的 **★条款、量化指标（人数/职称/工期/并发/准确率/驻场/不得更换等）、信创选型**
   > 逐条比对——看到 `[警告] 数据字典…可能漏抽/为空` **必须处理后再冻结**，绝不带着空/薄字典进入生成。
4. 写作规则见 `references/content_guide.md`（贴需求、颗粒度一致、衔接、控篇幅、**避免短语碎片**、信创）。

### 阶段二 · 逐叶生成（v4-flash，产出 content.json）
```bash
python scripts/generate.py plan.json content.json        # 离线跑通加 --mock
```
- **生成单位是"叶子标题"**（大纲里底下没有子标题的节点，按有无子标题判断、不看层数）：
  非叶子标题只输出标题；叶子调 `deepseek-v4-flash` 写正文，可在其内部按需加更深一层子标题（≤5级）。
- **子部分总述**：叶子若用多个内部小标题（会渲染成「1）」「2）」）分述子部分，则在第一个
  小标题前必须先写一段总述段落（约200～300字）统领全节，不得一上来就进第一个小标题；
  不分小标题则无此要求。分块续写的后续部分不再重复总述。
- 每次注入 **数据字典 + 完整大纲 + 本叶 brief/aspects(逐方面展开)/min_words/关键词/模板/字数预算 + 前文滚动摘要**，
  独立调用只做"局部扩写"；`aspects` 逐条要求成段论述，实际字数下限取 `max(word_budget, min_words)`，`max_tokens=20000`。
- **大叶子自动分块（仅兜底）**：正常情况下超大叶子已在规划阶段被拆成小叶子
  （`--split-threshold`，默认 6000），走不到分块。仅当拆分被禁用、失败或叶子已到第 5 级时，
  `word_budget` 超过 `--chunk`（默认 8000 字）才拆成多次顺序调用、续写追加到同一标题下。
  v4 输出上限 384K tokens，长度不是约束——阈值防的是超长单次生成的质量/字数交付衰减。
  续写块会收到已写小标题清单并被要求序号顺延；分块叶子的关键词在**末块强制补齐**
  （前面块自然覆盖），不留检查盲区。
- **断点续跑**：每写完一个叶子即落盘 `<输出>.ckpt.json`，中途崩溃直接重跑同一命令自动续上；
  `--fresh` 从头重来。全量完成后断点文件自动删除。
- 每叶产物过 `validate_content`，字数偏差/关键词缺失带提示重试；最后打印"叶子 字数/预算"报告。
  字数按"汉字 + 英文单词/数字串"计，JSON 解析失败的诊断文件写到**当前工作目录** `json_debug/`。
- 用户结构完全保留：脚本按 id 遍历，绝不改标题文本/层级/顺序。

**模式 B（手写直填）**：自己写 `content.json`（结构见 `references/content_schema.md`），
表格优先、figure 占位省略 `img`，**不手写任何编号/序号**，引擎自动生成。

### 阶段二之半 · 一致性检查（模式 A 必做）
```bash
python scripts/check_consistency.py content.json plan.json
```
以 plan.json 为基准核对成稿：**指标矛盾**（同一指标出现打架数值）、**得分点漏应答**
（某节缺 must_keywords）、**术语不统一**（出现禁用同义词）。有错误就**定点重写**相关章节
（可单独对该节再跑一次 generate 思路，或手改 content.json）后重检，直到通过。

### 阶段二之半B · 界面效果图（涉及功能开发/升级时）
成稿里"xx功能/xx界面/xx模块"类的 figure 占位，可生成高保真界面效果图替换占位框
（规范见 `references/mockup_guide.md`）：
1. 调 DeepSeek 批量生成**静态单文件 HTML 界面稿**到 `mockups/`（文件名=图题，
   自动回填的匹配依据）。脚本会为每张图收集业务上下文（标题路径、同章模块名做侧栏
   菜单、前文段落、术语字典），界面走政企后台骨架 + Element Plus 风格：
   ```bash
   python scripts/gen_mockups.py content.json plan.json --dir mockups
   ```
   默认只处理图题含"界面"的 figure（`--pattern` 可改）；个别生成不满意的，
   删掉对应 html 重跑，或人工改 html 后直接截图。
2. 截图并回填（本机 Edge 无头模式，零依赖）：
   ```bash
   python scripts/render_mockups.py mockups/ --attach content.json
   ```
3. 图题编号"图x-x"由排版引擎自动维护，增删图无需改序号。
   架构图/流程图不适用本流程（保留占位框或另行制图）。

### 阶段三 · 生成文档
```bash
pip install python-docx --break-system-packages   # 首次需要；配图占位另需 Pillow
python scripts/build_docx.py content.json 投标文件.docx
```
`build_docx.py` 会**先自动校验** content.json 再排版（内置 `validate_content.py`）：
- **错误**（空表头、表格列数不齐、非法块类型、空标题/段落等）会**中止生成**，按提示修正后重跑。
- **警告**（手写编号、短语碎片、标题跳级、配图缺失等）打印出来但不阻断，建议逐条处理。
- 也可单独跑校验：`python scripts/validate_content.py content.json`。
- 极少数情况下要跳过校验强行生成：`python scripts/build_docx.py content.json out.docx --no-validate`（不推荐）。

校验通过后引擎自动完成全部排版：A4 页边距、五级标题、列表序号、全框线表格、图表分章编号、
三段分节、自动目录域、正文页码。

> **所有排版参数集中在 `scripts/format_config.json`，无需改代码**：页面/页边距、中英文字体与
> 颜色、正文、五级标题、序号标题、三级列表、表格、配图、目录、页码——每个参数都带 `_说明`
> 注释，直接改数值即可，改完重跑 `build_docx.py` 生效。单位见文件头注（cm=厘米，pt=磅，
> 字符=1个中文字宽；对齐填 居中/两端对齐/左对齐/右对齐）。
> - **查找优先级**：`--format-config 指定路径` > `content.json 同目录` > `脚本同目录` > 内置默认。
>   因产物默认落在大纲同目录，把改好的 `format_config.json` 放到大纲目录即对本项目生效，
>   不影响其它项目。
> - **零回归**：JSON 缺失或某字段没填时，缺的部分自动回退到内置默认（即原规范），行为不变。
> - `run_all.py` 用 `--format-config 路径` 显式透传；不给则由 `build_docx` 自动按上述优先级查找。
> - 想临时用另一套排版：`python scripts/build_docx.py content.json out.docx --format-config 我的排版.json`。

> **序号标题（「1）」「2）」「（1）」「①」等末级降级/叶内小标题）缩进与正文完全一致**：
> 左侧 0 字符、首行缩进 2 字符（不按 marker 层做额外左缩进），仅靠序号样式区分层级，
> 避免与正文错位。

### 阶段四 · 验证（不可跳过）
排版正确性必须眼见为实：
1. 转 PDF 抽查：
   ```bash
   python <docx技能路径>/scripts/office/soffice.py --headless --convert-to pdf 投标文件.docx
   pdftoppm -jpeg -r 120 投标文件.pdf page && ls page-*.jpg
   ```
   读取目录页、若干正文页图片，逐项核对 `references/format_spec.md`：
   页边距、标题居中加粗三号、正文小四 1.5 倍缩进、列表序号层级、表格全框线表头加粗、
   图题在下加粗、页码居中且正文从 1 开始、无空白页、无封面页。
2. 内容自查：对照评分映射表确认无遗漏；抽查若干段落确认不是 AI 腔、颗粒度一致、
   指标全篇一致。
3. 提醒用户：用 Word 打开后按 `Ctrl+A` 再按 `F9` 更新目录与页码域（首次打开通常会自动提示）。

> 目录页码依赖 Word 的域更新。LibreOffice 转 PDF 时目录可能显示为占位文字，
> 这是正常的——以 Word 打开更新后为准；正文页码不受影响。

## 文件导航
- `references/content_schema.md` — content.json 的字段定义（写 JSON 前必读）。
- `references/content_guide.md` — 内容质量规则（贴需求/去AI腔/信创/衔接/篇幅）。
- `references/format_spec.md` — 排版规范明细与改参数位置（排版有特殊要求时查）。
- `references/plan_schema.md` — plan.json 结构（大纲树 + 页数规划 + 叶子字段，写/审 plan 前必读）。
- `scripts/outline_from_docx.py` — 大纲 docx→outline.json 确定性提取 + `--check` 转写校验（阶段一入口防错，必用）。
- `scripts/plan.py` — 规划脚本（v4-pro 理解 + Python 算页数 → plan.json）；数据字典由**独立调用**
  抽取（确定性候选甄别 + 空/薄自动补抽 + 覆盖率告警），不与叶子回填混调。
- `scripts/page_plan.py` — 篇幅算术模块（叶子识别、10页兜底、按权重分页，可单测）。
- `scripts/generate.py` — 逐叶编排器（plan.json →遍历大纲树、叶子调 v4-flash→ content.json）。
- `scripts/deepseek_client.py` — DeepSeek API 客户端（读 DEEPSEEK_API_KEY 环境变量）。
- `scripts/check_consistency.py` — 成稿一致性检查（指标矛盾 + 得分点覆盖 + 术语统一 + 参考资料审查报告 + 暗标查漏）。
- `scripts/references.py` — 参考资料解析/章节切片/相似度匹配/绑定 + 三模式重建（adapt/keep_headings/verbatim，可选功能，不用则零介入）。
- `examples/sample_outline.json` — 示例用户大纲（深度不齐，演示叶子）。
- `scripts/build_docx.py` — 排版引擎（content.json → docx），生成前自动校验；排版参数读 `format_config.json`。
- `scripts/format_config.json` — 排版参数总配置（页面/字体/正文/标题/列表/表格/配图/目录/页码），带 `_说明` 注释，改数值即改排版，无需动代码。
- `scripts/validate_content.py` — content.json 校验器（结构错误 + 手写编号/短语碎片 lint）。
- `scripts/make_placeholder.py` — 占位图生成器。
- `scripts/run_all.py` — 一键编排（plan→审核闸口→generate→一致性闸口→界面图→build_docx）。
- `scripts/gen_mockups.py` — 调 DeepSeek 为界面类 figure 批量生成 HTML 界面稿。
- `scripts/render_mockups.py` — 界面稿 HTML 批量截图(Edge 无头) + 按图题回填 content.json。
- `references/mockup_guide.md` — 界面效果图规范（命名约定/高保真要点/视觉规范）。

## 常见坑
- **最大事故源：转写大纲时被评分表带偏**——把评分因素当章节、把子级拉平成评分条款列表。
  一律用 `outline_from_docx.py` 提取+校验，结构只认大纲文件。
- 不要在内容里手写标题编号/列表序号——会和引擎自动编号重复。
- 表/图编号按所在一级章节分章计数，跨章自动重置，无需干预。
- 招标文件若规定了与默认不同的排版（如标题字号、目录级别范围、页边距、行距等），
  改 `scripts/format_config.json` 对应字段即可，无需动代码；改完重新生成并转 PDF 核对。
- 篇幅不够时靠增加指标表、流程拆解、分点展开来撑，不要写空话注水。
- **数据字典漏抽**：字典是全篇唯一事实源，漏一条指标全篇都缺。规划阶段已加三道保险——
  独立调用专抽字典、从原文确定性捞取候选行喂模型甄别、空/薄自动补抽并告警；但冻结前仍须
  对照 ★条款与量化要求人工复核（人名/logo/隐性要求仍需人眼把关）。
- **参考章节写得跑题、与参考相差太大**：根因是"精准绑定的大叶子被拆分"——拆分把 `ref` 留在
  父节点、子叶不带 ref，生成期退化成"继承·弱借鉴"（`auto=True` 弱措辞），还被逼着从相似度
  自动匹配的窄切片扩写大字数。已修复：**带自身 `ref` 的叶子一律不拆分**（整叶保留走强绑定分支），
  **精准绑定整节注入不再截到 3000 字**（`OWN_CAP_CHARS=12000`），**支持一节绑定多份参考**（`ref`
  写成数组，合并注入）。审查时看 `check_consistency.py` 的参考报告确认绑定章节是 `auto=False` 强绑定。
- **绑定了参考但整章像纯生成、参考没注入**：根因是 `section` 对不上（旧版 `find_section` 不认点号
  路径；或章节号写错、参考文件被改动），匹配返回 None → 绑定失效 → 退回纯大模型生成，成稿与参考
  相差极大。**两条稳妥锚点**：①用户看 `pair`/`show` 输出时，绑其打出来的**层级编号** `1.1.1`
  （同源、唯一无歧义）；②用户直接开原文件时，绑**标题原文**，重名用点号路径 `"祖先.目标"` 消歧。
  **切勿照 Word 界面上显示的自动编号绑**——那些号不在正文里、引擎按位置现编，可能与界面整体错位。
  **这类失败现在不再静默**：精准绑定没解析上时会被记为 fail-loud 项，
  `check_consistency.py` 以 **`[错误]`（非零退出）** 醒目报出「章节 X → 文件 Y「节 Z」：未匹配原因」，
  `generate.py` 日志也会打 `⚠ N 处精准绑定未匹配`。看到就核对章节号/标题后重绑、重跑 generate。
  （注：自动匹配相似度过低而退回纯生成属设计内兜底，不报错，只在报告里按 `auto=True` 列出。）
