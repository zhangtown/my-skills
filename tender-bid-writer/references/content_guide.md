# 内容写作指南 (Content Writing Guide)

排版引擎保证"好看"，这份指南保证"能中标"。写每一个字之前，先把采购需求和评分标准
摆在面前——投标文件的唯一读者是评标专家，他们手里拿着评分表逐条打钩。

## 一、紧扣采购需求与评分标准

1. 先把招标文件里的"采购需求 / 技术要求 / 评分办法"逐条抽出来，做成一张映射表：
   每一条评分点 → 对应到大纲的哪个章节 → 用什么内容应答。写作时对着这张表写，
   确保每个得分点都有正面、明确的应答，且用词尽量贴近评分表的原话（评委好找、好打分）。
2. 评分标准里出现的关键词（如"全流程""一张图""国产化""容灾""运维响应时间"），
   要在对应章节里原样出现并展开，不要换成同义词让评委对不上号。
3. 有量化指标（并发数、准确率、响应时间、可用性）的，正文要给出**具体数值承诺**，
   并尽量用表格列出，比纯文字更醒目、更易打分。

## 二、同级章节颗粒度一致

大纲里并列的二级标题，其下展开的深度、结构、字数应当大体相当。比如 3.1、3.2、3.3
都是"子系统设计"，那么三者都应包含"功能说明 / 技术实现 / 关键指标"这样平行的结构，
而不是 3.1 写了三级展开、3.2 只有一段话。颗粒度参差会让标书显得仓促、不专业。

**做法**：先为同一组并列章节定一个统一的内部小结构（一个"模板"），再逐个填充。
并列章节里如果某一节只够写成短语清单（如"界面简洁、国产 UI；操作步骤≤5 步"），
说明这块内容没吃透——应当补充实质性应答（怎么做、做到什么程度、有何承诺），
而不是用碎片凑出结构。

## 三、全篇衔接成一个整体

各章节不是孤立的，要像一篇文章而非拼凑：

- **不重复**：总体架构在"技术方案"章讲清楚后，后面章节引用即可，不要再整段重述。
- **不矛盾**：前面承诺"系统并发≥1000"，后面就不能写"≥500"；术语、产品名、指标全篇统一。
  建议维护一个"术语与指标对照表"，全篇引用同一份。
- **有过渡**：章节开头用一两句承上启下（"在前述总体架构基础上，本章细化……"），
  让阅读连贯。
- **前后呼应**：项目理解里提出的难点，要在技术方案里给出对应的解决措施，形成闭环。

## 四、篇幅控制

主负责人给每个大章节规定了页数。换算按正文排版样式查表（实测值，宋体、A4 默认页边距）：
四号=固定值22行距 860 / 1.5倍 731 / 单倍 953 字每页；小四=固定值22 1031 / **1.5倍 883（本排版规范默认）** / 单倍 1299 字每页。
含表格/图占位的页字数相应减少。

- 写之前按页数预算估算每章字数：`目标字数 ≈ 页数 × 每页字数`（默认 883），再按二级标题数量摊分，
  得到每个二级标题的字数预算，避免某节过长挤占别节。
- 撑篇幅时优先用"有信息量"的方式：增加指标表、流程拆解、分点展开、案例说明，
  **不要靠空话注水**。评委一眼能看出注水。
- 有明确字数上限的，严格不超；用上限的 85%–95% 为宜。

## 五、避免"一眼 AI 出品"（重要）

这是用户特别强调的。AI 腔的典型特征要刻意规避：

1. **避免"短语碎片堆砌"（核心）**。不要把章节内容写成一串用顿号/分号连接的短语或
   四字词组——那是提纲不是应答。每个要点都要展开成**完整句子**：有主语
   （通常是"我方／系统／项目组"）、有谓语动词，说明**怎么做**和**做到什么程度**，
   并带具体做法或数值。
   反例（短语碎片，禁止）：
   > 界面简洁、国产 UI；操作步骤≤5 步；支持可视化、钻取；国产浏览器适配。

   正例（完整应答）：
   > 系统界面遵循国产化 UI 规范设计，布局简洁、风格统一。常用业务的操作路径均控制在
   > 5 步以内，降低使用门槛。数据展示支持图表可视化与逐层钻取，用户可从汇总指标
   > 下钻到明细记录。前端已完成与主流国产浏览器的适配测试。

   句子长短服从表达需要，**不要为了"短"把完整意思切碎，也不要一句话套多层从句拉得过长**。
   唯一判断标准：每句话是否独立成立、是否在正面应答得分点。
2. **`list` 块只用于真正的并列枚举**，其条目也应是有信息量的短句而非光秃秃的四字短语；
   不要用短语清单替代本该展开的正文应答。
3. **少用 AI 高频套话**：避免"赋能""抓手""闭环""全方位多层次""综上所述""值得注意的是"
   "在当今……的背景下""不仅……而且……"这类空泛连接。用具体动词和名词。
4. **避免机械排比和三段式万能结构**。不要每节都"一是…二是…三是…"。结构要随内容变化。
5. **少用破折号长插入、少用分号堆叠**。多用短句号。
6. **加入项目特定的具体信息**：真实的技术选型、具体的部署方式、明确的数值、本地化的
   表述，让内容"长在这个项目上"，而不是放之四海皆准的通用模板。
7. **适度的人称与务实语气**："我方将…""我们建议…""项目组负责…"，比纯客观陈述更像
   投标人写的。

## 六、隐性硬要求：国产化 / 信创

除非招标文件另有说明，技术方案默认满足信创要求，并在合适章节明确写出：

- **基础软硬件**：服务器采用鲲鹏/飞腾等国产 CPU；操作系统采用麒麟/统信 UOS；
  数据库采用达梦/人大金仓/openGauss；中间件采用东方通/金蝶天燕等国产中间件。
- **适配与兼容**：声明系统已完成与上述信创软硬件的适配测试，提供适配清单。
- **自主可控**：核心代码自主开发，不依赖受限的境外组件，满足等保与密评要求。
- 在"技术方案""产品选型""安全保障"等章节自然带出，不要生硬堆砌一段了事。
- 若招标文件给了具体信创目录或比例要求，严格对标其条款。

## 七、写作产物

最终把内容组织成 `content.json`（结构见 `content_schema.md`），交给排版引擎。
写 JSON 时只管内容：标题文本、段落、列表项、表格数据、图题——**编号和序号一律留空，
引擎自动生成**。
