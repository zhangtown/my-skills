# 图标设计与多层品牌核对

图标是那种"做对了没人夸、做错了天天被看见"的东西。这一篇是两轮返工换来的经验：
第一版（深蓝底 + 一页纸）被否决，理由是**通透度不够**；第二版按飞牛官方应用的路子重画才通过。

## 一、飞牛官方那套风格（照着做就不会难看）

三个词：**浅底、通透玻璃、只在主体上给一处高饱和。**

1. **底色是浅色渐变，不是纯白也不是深色块**。纯白在白底页面上会"糊掉"，看不到轮廓；
   深色块不"通透"。用带一点点色相的浅渐变（例：`#eef5fd → #d3e4fb`）。
2. **主体做成磨砂玻璃**：亮色渐变 + 顶部一条高光 + 左侧一道镜面反光 + 内部几条深浅不一的白/浅色线
   （代表内容）。比纯色块精致得多，也贴合"这是一块玻璃"的官方观感。
3. **高饱和只用在主体的一处**（比如主体本身，或一个小徽标），周围全是低饱和的浅色。
   一图三处高饱和就会像十年前的扁平图标。
4. **柔和投影 + 极淡描边**：主体下方一层高斯模糊的柔影，让它从底板上"浮"起来；
   描边用同色系极淡的一层，是为了在白底上仍有边界。
5. **圆角约 22%**（256px 图上约 56px 半径），跟系统图标一致的呼吸感。
6. **缩到 16px 还能认**：别堆元素。主体占画面 60~70%，细节最多两三处；
   小尺寸靠"剪影 + 一处高饱和"辨认，不靠细节。
7. 同一家的多个应用**共用一套几何语言**（同样的底、同样的玻璃手法、同样的投影），
   换主体即可——用户一眼认出是一家的。

自己看不准就把尺寸摊开看：拼一张 **16 / 24 / 32 / 64 / 128 / 200px × 白 / 浅灰 / 深底** 的对照表，
小尺寸和深底是最容易翻车的地方（深底上没有描边就会消失）。

## 二、用 Go 生成（可复现、可微调）

不要手绘 PNG：改一次要重导一遍，多尺寸还会不一致。用一个小程序画：
`scripts/mkicon/main.go` 是跑通的模板，思路是**符号距离场逐像素渲染**：

- 形状用 SDF 表达（圆角盒、圆、椭圆、多边形的并集），抗锯齿天然正确；
- 填充线性渐变（按投影距离插值颜色）；
- 柔影 = 对偏移后的形状做一次羽化（按距离衰减 alpha）；
- **3 倍超采样后盒式降采样**，边缘干净；
- **纯标准库**，没有第三方依赖，`go run ./tools/mkicon` 就能出图。

一次写出全部产物（顺序与路径都很关键）：

```
ICON.PNG            64×64   应用中心/桌面图标
ICON_256.PNG        256×256 同上（大尺寸）
icon.png            256×256 浏览器标签页图标（程序里 //go:embed 用）
app/ui/images/icon_64.png   桌面 iframe 图标（config 里 icon_{0}.png 展开）
app/ui/images/icon_256.png
```

生成接口建议做成 `-out <包目录>`（模板已如此），这样一次就把 5 份写到位、不用手工拷。

### 两个必须记住的顺序/一致性问题

- **图标必须在编译之前生成**。程序常用 `//go:embed icon.png` 供 favicon 端点，
  先生成图标再 `go build`；顺序反了，NAS 上界面里永远是旧图标，而且你怎么查代码都没问题。
  `pack.sh` 里就把"生成图标"放在第一步。
- **256px 的三份产物应当字节一致**（同源），64/128 是同源降采样，md5 不同是正常的。
  核对时用 `file` 看尺寸与色彩模式（应为 RGBA）、用 md5 判断"是不是同一版设计"。

## 三、图标与名字出现在七层，改一次要全改

| # | 出现位置 | 来源 | 怎么核对 |
|---|---|---|---|
| 1 | 应用中心列表 / 桌面图标 | `/var/apps/<app>/ICON.PNG`、`ICON_256.PNG`（安装时拷过去） | md5 与仓库对比 |
| 2 | 桌面 iframe 里的图标 | `app/ui/images/icon_{64,256}.png` | 同上 |
| 3 | 浏览器标签页 favicon | 程序内嵌的 `icon.png`（或 HTTP 端点） | `curl /icon.png \| md5sum` |
| 4 | 应用内首页 hero | 前端内联 SVG（与图标同一套几何） | 页面上肉眼 + DOM 里有没有那个组件 |
| 5 | PIN 门 / 启动失败页 | 同一份 SVG 组件（**别只改首页**） | 逐个页面看 |
| 6 | 应用名字 | manifest `display_name` **和** `app/ui/config` 的 `title`（两处都要改） | 应用中心 + 桌面各看一次 |
| 7 | 页面标题 | 前端 `index.html` 的 `<title>`，或运行时注入 | 浏览器标签页文字 |

改名时容易漏的还有：`appname`（改它等于改 URL/网关前缀/数据目录，**能不改编就别改**）、
`gatewayPrefix`、`desktop_applaunchname`（必须与 `app/ui/config` 的键一致）、
应用内欢迎文档/示例内容的标题、README。

### 真实翻车现场

- **"手机浏览器上还是旧名字"**：两个原因叠加 —— ① NAS 上装的是旧包（改完代码没重新打包部署），
  ② 客户端缓存。**先确认 NAS 上的包是新的**（比对 `index.html` 与 JS 包的 md5/内容特征），
  再去清缓存，否则会一直在客户端侧白费功夫。
- **"图标还是旧的"**：见下一节，图标 URL 不带版本参数，天然长缓存。
- **起名撞车**：动手前搜一下有没有成熟产品同名同类。真实例子：原本叫「云记笔记」，
  与某成熟手写笔记 App 同名同类，容易让人以为是非官方客户端，因此改名。
  改名成本远低于上线后改名。

## 四、图标缓存：为什么用户看不到新图标

应用中心/桌面取图标走的是这种 URL（nginx 直接指向应用的 `ui` 目录）：

```
/app-center-static/serviceicon/<app>/ui/images/icon_{0}.png?size=256
/app-center-static/icon/<app>/icon.png
```

- URL 里 `{0}` 是**原样保留**的（不是占位符替换），也没有版本/时间戳参数 → 客户端按静态资源长缓存。
- **手机 App 的 WebView 会缓存得更久**，桌面浏览器刷新也不一定换。
- 验证的正确姿势：**开无痕窗口**看。无痕里是新的 → 服务端没问题，是用户端缓存；
  无痕里还是旧的 → 回去查服务端文件与那层"登记记录"。

服务端侧还有一层容易忽略的：**应用中心服务把应用清单读进内存**（`trim_app_center.service`），
手工往 `@appcenter` 里换文件不会触发它重扫；把服务重启一次（或走正规安装）才会重新读。
