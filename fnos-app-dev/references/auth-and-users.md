# 鉴权、PIN 与多用户数据

## 一、先决定：要不要自己鉴权

- **内嵌应用 + 只在飞牛桌面里用** → 网关已带身份，可以不鉴权。
- **内嵌 + 想要"打开应用再确认一次"**（比如笔记、私密数据）→ 加一个 6 位 PIN。
- **带端口应用** → 端口在局域网上裸奔，**必须**加密码（空密码 = 局域网友好是常见折中）。

PIN 不是加密：磁盘上的原始数据仍是明文。文档里要把这句话写出来，否则用户会误以为"加了 PIN 就安全了"。

## 二、PIN 的存法与生命周期

| 环节 | 做法 |
|---|---|
| 首次进入 | 提示设置 6 位数字，两次输入一致；两个输入框都 `type=password` |
| 存储 | **只存哈希**，写进数据目录（如 `$TRIM_PKGVAR/users/<uid>/pin.json`），绝不存明文、不回显。可直接照抄的一套：`{version, algo:"pbkdf2-sha256", iters:120000, salt, hash, updatedAt}`，salt 16 字节、key 32 字节、base64 存；校验用恒定时间比较。目录 `0700`、临时文件 `0600` + `os.Rename` 原子替换 |
| 解锁 | 校验通过 → 签发令牌（见下）；失败要限速：`<5 次不锁`、`<10 次锁 1 分钟`、`<15 次锁 5 分钟`、否则 `15 分钟`，锁定时返回 `429` + `Retry-After`，失败返回 `401` + 「PIN 不对，还能试 N 次」 |
| 修改 | 需要先解旧 PIN 或走已解锁会话 |
| 忘记 PIN | 文档里明确写"删掉数据目录里的 pin 文件即可重置"——否则用户会以为数据被锁死了。**这条必须写进 README** |
| 多用户 | PIN 按 uid 独立（与数据隔离策略一致），一个账号设了 PIN 不影响别的账号 |

把 PIN 放在**数据目录**而不是包里：包里是公开且升级会覆盖的，数据目录才是"你的东西"，
卸载时按向导决定是否删除。也顺带获得"备份数据 = 备份 PIN"的一致性。

## 三、令牌的三条通道（踩过的最贵的坑）

同一个令牌要能让客户端通过三种方式带上，缺一条就会出现"某些场景下一直让你重新输"：

| 通道 | 用途 | 注意 |
|---|---|---|
| **Header** `X-<App>-Token` | 前端所有 `fetch`/XHR 调用 | 首选。前端把令牌存 `localStorage`，每次请求带上 |
| **URL 参数** `?token=` / `?t=` | `<img src>`、下载/导出链接、`window.open`、WebView 兜底 | **只接受 GET/HEAD**：POST 会把令牌写进访问日志/表单，风险更大 |
| **Cookie** `ztnote_session` | 刷新页面不掉线、iframe 场景 | `HttpOnly` + `SameSite`；跨站 iframe 里可能被拦（见下） |

后端中间件按顺序取：Header → URL 参数 → Cookie；取到就校验 TTL，并把**来源通道**记进日志
（排查时一眼看出客户端到底走了哪条路）。

### 移动端 WebView 拦第三方 Cookie 的真实故障

**症状**：手机上 PIN 明明输对了（提示解锁成功），可下一步还是回到锁屏，一直让重输。
桌面浏览器完全正常。

**根因**：飞牛手机 App 把应用嵌在 WebView/iframe 里时，`Set-Cookie` 被当第三方 Cookie 拦掉
（跨站 iframe + `SameSite=Lax/Strict` 的默认行为）。后端日志表现为：解锁接口返回 200 且带
`Set-Cookie`，但紧随其后的请求里**既没有 Cookie 也没有令牌** → 又被判定为未解锁。

**修法**：不要依赖 Cookie。前端登录成功后把令牌存进 `localStorage`，之后：
- 所有 API 走 Header；
- 无法带 Header 的（图片、导出、新窗口）走 URL 参数；
- Cookie 作为附加通道保留（桌面浏览器更顺）。

**怎么快速判定是不是这个坑**：在中间件里把"令牌来源通道"与"是否拿到令牌"写到日志；
如果只有移动端失败、且那个客户端的后续请求里连 Cookie 都没有，基本就是这个原因。
自测时用真机（或 Chrome DevTools 手机模拟 + 第三方 Cookie 拦截）复现，别只看桌面。

## 四、多用户数据

### 网关透传身份

内嵌 / 走网关的应用能从请求头拿到当前飞牛账号，常见是 `X-Trim-Userid`（值为 uid）。
拿到 uid 就能做隔离；拿不到（比如直连端口）就得退化成共享数据或用应用自己的账号体系。
**先确认这个 header 在你的环境里到底叫什么名**（`curl -H` 试、或把请求头打日志），别照抄猜的名字。

**uid 会直接进文件路径，所以必须白名单校验**（否则就是路径穿越漏洞）：
非空、长度上限（如 32）、只允许 `[0-9A-Za-z_-]`，不合规就回落到一个固定的本地身份（如 `local`）。

**管理员标记不用来判权**：应用通常不需要区分管理员（入口对所有用户开放），
界面里顶多显示一个「管理员」徽标。真正的权限边界是「每人一份数据 + 各自的 PIN」——
这样也就不用在每个接口上做角色判断，少一大类绕过风险。

### 两种数据布局

```
按账号隔离（每个飞牛账号各一份）
$TRIM_PKGVAR/users/<uid>/workspace/…

全机共享（所有账号看同一份）
$TRIM_PKGVAR/<业务目录>/
```

选择原则：**"这是谁的私人东西吗？"** 是 → 隔离；是全局任务/下载/家庭共享库 → 共享。
混用也可以（共享配置 + 每账号数据），但要在 README 里写清楚哪个目录是什么，
因为用户备份时只想知道"我的东西在哪"。

### 升级时迁移老数据

作者从「没有 uid 概念」的旧版本升上来时，`$TRIM_PKGVAR/workspace` 这类目录要迁给某个默认账号。
做法：启动时若发现老目录且新布局不存在，就搬家给默认 owner（可用环境变量覆盖，
如 `ZTNOTE_LEGACY_OWNER`，默认 `1000`），并写一条日志。**迁移要幂等**：迁过之后再次启动不能重复搬
（判据：老目录里有真实数据、且目标账号还没有同名数据目录）。目标账号若已存在空壳目录，
要先删空壳再 `os.Rename`，否则会搬到一半失败。

### 文件属主与权限（一次真实的翻车）

应用以 root 跑（`config/privilege`），于是它写出来的文件默认是 `root:root 0644`、
新建目录默认 `root:root 0755`——用户的文件管理器、SMB、媒体库可能都进不去。

正确做法：**按父目录对齐**，并且只对齐不放大：

1. 先 `chown` 成父目录的 uid/gid，再 `chmod` 成父目录的权限位
   （顺序不能反：btrfs + ACL 继承的环境里先 chmod 会把属组位清掉）；
2. **只在本次真的新建时才对齐**，已存在的目录一根手指都不碰（用户可能自己调过权限）；
3. 不要硬写 `0755`——如果父目录是 `drwx------`，你写 0755 反而比用户自己的目录更宽松。

## 五、README 必须回答的三个问题

用户（包括三个月后的你）最需要知道的是：

1. **我的数据存在哪？**（给出 `$TRIM_PKGVAR` 的真实路径与目录含义）
2. **怎么备份？**（复制哪个目录；升级/卸载会不会动它）
3. **忘了 PIN / 想换个账号用怎么办？**（删哪个文件、数据在不在）
