# 界面层的坑（与平台无关，但每一个都真踩过）

飞牛应用通常是"网页装进桌面"，所以界面层的毛病会原样呈现给用户。这一篇记的是几个
**返工过、且一眼就能看出差别**的问题。

## 一、右键菜单太长（空间浪费的典型）

**现象**：正文右键菜单 21 项竖着排下来 700+px 高，一屏放不下；更要命的是
「无序列表 / 有序列表 / 引用 / 代码块」这几个标签**被挤成两行竖排**——因为左侧图标位用的是
两三个字的文字（`列表`、`引用`、`代码块`），把标签列挤窄了。

**根因**：把菜单当成"一列列表"来做。三处浪费叠加：单项高度、图标位的文字宽度、分组之间的分隔。

**修法**：
1. 宽屏时改成**两列**（`display: grid; grid-template-columns: 1fr 1fr`），高度立刻减半
   （21 项 → 约 372×363px，一屏放得下）。
2. 图标位**只放单字符**（`•`、`1.`、`"`、`</>`），不给文字标签留位；标签不再换行。
3. 窄屏（< 640px）放不下两列时**自动退回单列 + 菜单自身可滚动**，别硬挤成两列小字。
4. 分组之间的分隔线保留（它承担"这是另一类操作"的信息），但不要给每组加标题行。

**验收**：用真 CDP 鼠标事件（`Input.dispatchMouseEvent`）右键→量菜单矩形（宽/高）→
再看每个菜单项是否换行（`scrollWidth > clientWidth` 或行高异常）→ 三个视口各截一张图：
桌面（两列）、390px（仍两列）、320px（单列 + 可滚动）。

## 二、移动端横向溢出（"比屏幕稍微大一点"）

**现象**：手机上首页比屏幕宽一点点，底部出现横向滚动条。

**根因**：CSS Grid 只写了行、没写列：

```css
.shell { display: grid; grid-template-rows: var(--topbar-h) 1fr; }
```

隐式列的宽度是 `auto`，其**最小尺寸 = 内容的最小内容宽度（max-content）**。
顶栏里有个不换行的长内容，于是整个网格被撑到 396.7px，比 390px 的视口宽。

**修法**：显式写出列，并给所有可能撑宽的容器加 `min-width: 0`：

```css
.shell { display: grid; grid-template-columns: minmax(0, 1fr); grid-template-rows: var(--topbar-h) 1fr; }
```

同样的坑在 flex 里叫 `min-width: auto`，给子项加 `minmax(0, 1fr)` / `min-width: 0` 即可。

**验收**：量 `document.documentElement.scrollWidth` 与 `clientWidth`，列出所有
`getBoundingClientRect().right > innerWidth` 的元素——比肉眼找快得多。
宽度至少要过 320 / 360 / 390 / 414 / 768 / 900 / 1180。

## 三、客户端缓存：用户看不到新界面

**症状**：服务端已经是新版，用户那边还是旧界面（图标、文案、样式）。

**根因**：静态资源没有明确的缓存策略，客户端按启发式规则长缓存。

**修法**（服务端主动声明，别指望客户端自觉）：

- HTML/入口页：`Cache-Control: no-cache`（可再验证，但每次都校验）
- 带内容哈希的构建产物（`index-<hash>.js/css`）：`Cache-Control: public, max-age=31536000, immutable`
- 其它静态资源：短 `max-age`（如 300s）
- 条件请求支持 `ETag` / `Last-Modified`，命中就还 304

**排查**：先确认服务端文件是新的（比对 md5），再让用户开**无痕窗口**。无痕里是新的就到此为止，
不要继续改代码。

## 四、编辑类应用的界面约定（一次数据丢失换来的）

如果应用允许"直接编辑、实时保存"（没有保存按钮），这几条是硬要求：

1. **状态栏必须有明确初始态**：刚打开就显示「已保存」，而不是空白。
   空白会让用户不知道到底存没存——这是最容易被忽略、也最容易被用户吐槽的一条。
2. **状态要能回到"已保存"**：撤销/重做回到与"上次保存内容一致"的状态时，
   状态文案必须跟着回到「已保存」（否则会一直挂着"有未保存的改动"，用户以为出了问题）。
3. **保存是把"发送时的快照"写下去，不是把"当前编辑器内容"写下去**：
   请求在飞行中时用户可能继续输入；响应回来时不能拿旧快照覆盖编辑器，也不能用新输入覆盖已保存内容。
   做法：发送前取快照 → 请求 → 响应回来后只在"编辑器内容仍等于该快照"时更新基准点。
4. **保存要被节流并合并**：例如"停止输入 900ms 后保存、两次保存至少间隔 4s、
   最多拖 15s 必须落一次盘"。这比"每次按键都发请求"省得多，也比"只在离开时保存"安全。
5. **保存失败要不丢内容**：失败后保留脏状态与重试入口，并明确告诉用户"上次保存失败"。

## 五、其它高频小坑

- **悬停才出现的按钮在触屏上等于不存在**：`@media (hover: none)` 里让它常显（可以低透明度），
  或提供长按/点击替代。
- **浮层要夹在视口内**：用 `position: fixed` + 计算后 clamp 到 `[8, 视口宽高 - 8]`，
  否则贴着屏幕右下角的菜单会被裁掉一半。
- **依赖请求头的资源（图片/导出）在 iframe 与移动端容易掉令牌**：
  给这类 URL 走查询参数通道（见 `auth-and-users.md`）。
- **窄屏顶栏别塞产品名与 logo 的重复组合**：侧栏已经有品牌行了，顶栏再放一次纯属浪费一个高度，
  还会把可用宽度挤掉。窄屏优先保证"内容"和"返回/菜单"这类操作。
