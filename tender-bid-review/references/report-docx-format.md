# 审查报告 Word 格式规范（docx）

审查报告默认交付 Markdown 骨架给人扫读；**需要交给商务、法人代表或归档时，套本格式出 Word**。样式由 `scripts/report_docx/report_style.js` 统一控制，报告内容用 JSON 描述，二者分离——改版式不动内容，改内容不动版式。

```
报告 JSON ──► bash scripts/report_docx/build.sh report.json out.docx ──► 校验通过
```

- `scripts/report_docx/report_style.js` —— **格式唯一真源**（字体/字号/缩进/行距/底纹/页眉页脚/目录域）
- `scripts/report_docx/build.js` —— JSON → docx
- `scripts/report_docx/build.sh` —— 自动准备 `docx` 依赖（复用 kimi-docx 的共享依赖目录）＋ 构建 ＋ 调 `scripts/docx validate`
- `scripts/report_docx/example-report.json` —— 完整实战样例（东南大学电力网络场景仿真项目·诚迈科技），照它抄最快

## 一、版面与字体令牌

| 项 | 取值 | 出处 |
|---|---|---|
| 页面 | A4（11906 × 16838 twip），纵向 | `PAGE` |
| 页边距 | 上下左右均 2.54 cm（1440 twip），版心宽 9026 twip | `PAGE.margin` |
| 正文 | 宋体 + Times New Roman，小四（12 pt），行距 1.33，段后 7 pt，**首行缩进 2 字符**（480 twip） | `FONTS.body` / `SPACING.body` / `INDENT.firstLine` |
| 标题 | 黑体，H1 15 pt、H2 13 pt，加粗，深墨蓝 `#23343F` | `FONTS.head` / `SIZES` |
| 封面主标题 | 黑体 20 pt 居中；副标题宋体 13 pt 居中，海蓝 `#3C5865` | `SIZES.title` / `SIZES.subtitle` |
| 表格 | 宋体 10.5 pt，表头黑体加粗＋浅蓝底 `#EDF3F6`，框线 `#D3DDE1` 0.5 pt，单元格内边距 100/120 twip | `SIZES.table` / `COLORS` |
| 引用块 | 宋体 12 pt，左缩进 480、右缩进 360，浅灰底 `#F4F7F8` —— **专用于引招标条款原文与投标原文** | `quote()` |
| 小字注释 | 宋体 10 pt 斜体，浅灰 `#7E949E` —— 口径说明、免责声明 | `SIZES.note` |
| 页眉 | 报告标题，宋体 10 pt 加粗，海蓝，居中（全篇包括封面） | `buildDocument()` |
| 页脚 | 居中页码（`PageNumber.CURRENT` 域） | `pageNumber()` |
| 目录 | Word 原生 TOC 域 `TOC \o "1-3" \h \z \u`，带缓存条目，`updateFields` 已开启 | `tocField()` |

**色板语义**（不要随手加颜色）：

| 令牌 | 色值 | 用途 |
|---|---|---|
| `dark` | `#23343F` | 标题、正文强调 |
| `primary` | `#3C5865` | 副标题、页眉、圆点符号、表题 |
| `light` | `#7E949E` | 注释小字 |
| `border` | `#D3DDE1` | 表格框线 |
| `fill` | `#EDF3F6` | 表头底纹 |
| `fillHigh` | `#F7E4DC` | **风险行底纹**——自相矛盾的证据行、命中废标条款的行 |
| `fillWarn` | `#FBEFE9` | 次要提示行（备而不用） |

`fillHigh` 是这份报告唯一的"视觉重音"。一张表最多标 1–2 行，标多了等于没标。

## 二、报告 JSON 的块类型

`sections` 是块数组，按顺序渲染。一个块对象可以同时带多个键（按 `h1 → h2 → p → lead → quote → bullets → list → note → table` 的固定顺序输出）。

| 块 | 写法 | 渲染效果 |
|---|---|---|
| 一级标题 | `{ "h1": "二、废标风险：确定性缺失（P0）" }` | 黑体 15 pt，映射 `Heading1`，进目录 |
| 二级标题 | `{ "h2": "2.1 投标保证金缴纳凭证整页缺失" }` | 黑体 13 pt，映射 `Heading2`，进目录 |
| 正文 | `{ "p": "……" }` | 首行缩进 2 字符；`{ "p": "…", "indent": false }` 取消缩进 |
| 引导词句 | `{ "lead": ["位置：", "投标文件第 212–214 段……"] }` | 黑体加粗标签 + 正文；第二项传 `""` 就是只出标签（「原文：」「违反条款：」「整改要求：」） |
| 原文引用 | `{ "quote": "214　待诚迈提供" }` 或 `{ "quote": ["第一段", "第二段"] }` | 浅灰底纹引用块，逐条缩进 |
| 圆点列表 | `{ "bullets": ["…", "…"] }` | ● 海蓝符号 + 正文，左缩进 360 |
| 编号清单 | `{ "list": ["【必改·P0】…", "【现场】…"] }` | 序号自动生成，悬挂缩进，用于整改优先级清单 |
| 小字注释 | `{ "note": "（本报告基于电子版文件审查……）" }` | 斜体浅灰小字，放章末 |
| 表格 | 见下 | 100% 宽，表头自动浅蓝 |
| 分页 | `{ "pageBreak": true }` | 另起一页（长报告分章时用） |

### 表格写法

```json
{
  "table": {
    "caption": "表 2　两台服务器品牌型号的两种写法",
    "head": ["出处", "详细规格型号", "品牌", "制造商、产地"],
    "widths": [22, 24, 20, 34],
    "highlight": [0, 1],
    "rows": [
      ["分项报价表", "ACM-01-SEV", "诚迈科技", "诚迈，南京"],
      ["供货一览表", "ThinkServer SR658H V2", "联想", "联想、中国"]
    ]
  }
}
```

- `widths` 是**列宽权重**，内部按比例归一化到版心宽度（9026 twip），不必自己凑总数；省略则等宽。
- `highlight` 是**行下标**（0 基），命中的行加 `#F7E4DC` 底纹 —— 用来把"两处互相矛盾的说法"钉在同一张表里给评委看。
- 单元格文本里的 `\n` 会拆成多段。
- 表格行数多时注意：**同一张表的分页会重复表头**（`tableHeader: true` 已设）。

## 三、章节骨架（与 SKILL.md 第四步的 Markdown 骨架一一对应）

Word 版沿用同一套骨架，只把 Markdown 表格换成带底纹的 Word 表格：

| 章节 | 建议块型 | 说明 |
|---|---|---|
| 封面 | `title` / `subtitle` / `meta.rows` | `meta.rows` 固定 7 行：项目名称、项目编号、被审文件、对照文件、投标截止/开标、审查范围、报告性质 |
| 目录 | `toc` | 传 `true` 自动从 h1/h2 生成（页码留空，更新域后填充）；传数组则用自带页码 |
| 总体结论 | 1 段正文 + 1 张两列表 | 结论项 / 结论；**结论项固定 5 行**：是否必然废标、P0、P1、P2、国外品牌（本项目未涉及国外品牌时，第 5 行写"未涉及"或删除） |
| 一、废标条款逐条对照 | 表格，`highlight` 标命中的条款行 | 列：条款 / 要求 / 投标文件实际 / 判定（通过·命中·无法从电子件核实） |
| 二、▲项证明材料核验 | 表格 | 列：▲项 / 材料有无 / 形态 / 有效DPI / 盖章 / 图文对应 / 判定 |
| 三、格式与用语问题 | 表格 | 列：编号 / 位置 / 问题 / 建议 |
| 四、文档痕迹问题 | 表格 | 同上；批注作者、creator、rsid、缩略图逐项列 |
| 五、内容自相矛盾 / 失实陈述 | 每处一节：`h2` + `lead("位置：")` + `quote(投标原文)` + 风险段 + `bullets(整改要求)` | 引原文时必须用 `quote` 块，便于对照 |
| 六、签章清单（逐页） | 表格 | 模式 B 的核心，列：页码 / 材料名称 / 需盖章 / 需签字 / 状态 |
| 七、文件外待确认事项 | 表格（打钩表） | 份数、密封、装订、保证金到账、授权代表到场、现场演示 |
| 八、流标风险分析 | 正文 + 可选表格 | 三道闸口与有效家数 |
| 九、整改优先级 | `list` | 每条以 `【必改·P0】`/`【建议·P1】`/`【现场】` 开头 |
| 附：审查方法与范围 | `bullets` + `note` | 招标侧取值、投标侧取证、判定口径、免责声明 |

**只出 Word、不出 Markdown 时**，也应当遵守 SKILL.md 的分诊口径 —— 格式只负责排版，**不替你做 P0/P1/P2 的分级判断**。

## 四、构建与校验

```bash
cd <tender-bid-review 技能目录>

# 一键：准备 docx 依赖 → 构建 → 校验
bash scripts/report_docx/build.sh report.json "/abs/path/【审查报告】xxx.docx"

# 只看构建，跳过校验
bash scripts/report_docx/build.sh report.json out.docx --no-validate

# 只构建
node scripts/report_docx/build.js report.json out.docx
```

`docx` 依赖解析顺序：本地 `node_modules` → 环境变量 `DOCX_NPM_PREFIX` → `~/.cache/claw-office-docx/npm`（由 kimi-docx 技能的 `scripts/setup_node_env ensure-docx` 预置，build.sh 会自动触发）。**不需要在项目目录里装依赖、也不需要在项目目录里建软链接。**

校验用 kimi-docx 技能的 `scripts/docx validate`（会解包、做安全修复、必要时重打包）。`Error:` 是阻塞项，必须修掉或如实上报；`Warning:` 可单独披露。

**视觉终检（可选但推荐）**：装了 LibreOffice 时
`bash <kimi-docx>/scripts/docx render out.docx <outdir>` 会转 PDF 并逐页出图 + 联系表，用来确认表格没串行、目录没空白页。本机没装 LibreOffice 时跳过，并在交付说明里注明"未做渲染视觉核验"。

## 五、踩过的坑

1. **`PageNumber` 不是构造函数**。docx v9 里它是域占位常量，写 `new TextRun({ children: [PageNumber.CURRENT] })`，写成 `new PageNumber()` 直接抛 `TypeError: PageNumber is not a constructor`。
2. **页脚用 `PageNumber.CURRENT`**，不要自己拼 `<w:fldChar>`——手拼容易漏 `separate`/`end` 导致页码不显示。
3. **目录必须更新域**。生成的目录是"缓存条目 + 脏域"，打开时 Word/WPS 会提示更新；没提示就全选按 F9。报告里的估算页码只是缓存显示值，**不要把它当成真实页码写进正文引用**。
4. **列宽不要自己凑总和**。交给 `widths` 权重归一化，否则改版心或改边距时表格会溢出。
5. **表格底纹是分诊信号，不是装饰**。只在"同一事实两种说法"或"命中废标条款"的行上用 `fillHigh`。
6. **JSON 里避免出现需要转义的引号**。中文引文一律用 `「」`、`〔〕`，省得 `\"` 满屏。
7. **页眉会出现在封面页**。正式归档件若要求封面无页眉，需要在 `buildDocument()` 里加 `titlePage` 区分首页页眉。
8. **构建器只吃结构化 JSON**。审查结论本身（分诊、条款引用、页码定位）由审查过程产出，不要指望生成器替你判断——**报告里每个数字都要能回到招标/投标原文复核**。
9. **位置列必须写被审文件的页码，不能写段落序号或内部编号**。实测翻车：首版把位置写成 docx 段落序号（`P2717`），用户第一句就是「P2717 是什么鬼 哪有这么多页」——这类编号对方翻不到，报告可信度直接打折。
10. **页码映射先建后写**。用 WPS COM 把被审文件导 PDF（`pages = doc.ComputeStatistics(2)` 取总页数），逐页抓首行/标题文本，建立「节标题（或表）→ 印刷页码」锚点表；先确认页码基准（实测：全文 337 页、页脚印刷 **1–336**、首页无编号 ⇒ **印刷页码 = PDF 物理页序 − 1**），再拿锚点表里的页码写报告，并**把基准写进「附：审查方法与范围」**。多页材料写区间（「第 225–237 页，每页一张」），表格要带上表名与页码（`第 30 页「六、商务条款偏离表」第 7 行`）。
11. **报告自己的目录页码要回读校验**。构建 → 导 PDF → 逐页扫 `h1`/`h2` 文本取实际页码，与目录缓存条目逐条比对（WPS 导 PDF 会刷新目录域，实测一致）；顺手扫正文块越界（A4 595×842 pt，版心右界 523 pt 为正常边界，y ≈ 807 pt 以上属页脚不算越界）。
12. **同一指标的聚合数字只能有一个口径**。实测：低清晰度材料先报「5 张」，换算法后是「7 张」——同一稿里若既有「209 张中 169 张达标」又有「仅 5 张不达标」，读者一眼就看出自相矛盾。**换算法就全篇重算再定稿**，口径（按 PDF 出图尺寸 × 实际像素）写进附录。
