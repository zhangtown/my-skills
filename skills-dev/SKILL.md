# 技能开发（skills-dev）

技能的价值不在文档写得多漂亮，而在**别人（或未来的你）拿着它去做同一件事，结果真的更好**。
所以这份技能的核心不是"怎么写 markdown"，而是：**从真实经历里提炼 → 用评测验证 → 按证据改稿**。
凡是没经过验证的说法，都要在技能里标明是推断。

## 一、先判断：这该不该做成技能

不是所有经验都值得固化。三条判据，满足两条才做：

| 判据 | 意味着 |
|---|---|
| **会重复发生**：同一类任务预计还会做很多次（做第二个同类 App、接第二个同类需求） | 一次性的排障结论更适合写进项目文档 |
| **有非显然的坑**：新手（或三个月后的自己）大概率会踩，且踩了要花半天以上 | 显然的常识不值得占篇幅 |
| **有可复现的判据**：能写出命令、字段、数字来验证"做对了" | 纯靠感觉的经验只能写成提醒，别包装成流程 |

反过来，**明确不该做的**：把某个项目的业务细节抄成技能（那是项目文档）、把一次性的环境事实写成技能
（换机就失效）、把"要谨慎""要注意"这类无判据的叮嘱塞进技能（模型看完不知道该做什么）。

## 二、技能的解剖与目录边界

```
<技能名>/
├── SKILL.md          # 必需。frontmatter(name/version/description) + 正文
├── references/       # 按需加载的细节：一个主题一个文件，SKILL.md 里指路
├── scripts/          # 可复制执行/改编的模板（打包、安装、生成器…）
├── assets/           # 产出物里要用的模板/字体/图标
└── evals/evals.json  # 评测集（可选，但客观类技能强烈建议）
```

**一个技能目录只装一个技能**——这是踩过的坑：两个技能挤在同一目录会让快速校验、评测、引用路径全部串台，
表现是"评测里量到的能力其实来自另一个技能"。技能之间要互相引用就用相对路径 + 明确写"这是外部技能"。

**frontmatter 三条**：

- `name`：小写连字符，与目录名一致；跨端都靠它识别
- `version`：改动就升，便于判断本机装的是哪一版（两端目录里可能各有一份）
- `description`：**唯一的触发机制**，写"做什么 + 什么时候用"，并且要**稍微推一把**——模型的倾向是
  该用时不用。把所有"when to use"信息放这里，不要放正文（正文触发时才会被读）

## 三、制作流程（七步）

1. **访谈意图**：先问清——要解决什么、什么时候该用、产出长什么样、有没有可验证的判据。
   如果对话里已经做过一轮真实工作，**优先从对话/项目里提取**（用了什么工具、什么顺序、踩了什么坑、用户纠正了什么），
   让用户只填空缺，而不是从头描述。
2. **提炼事实**：让每个说法都能追溯到"哪个文件哪一行、什么命令、什么输出"。数不清就别写。
   提炼时特别收集三类东西：**实测数字**（超时几秒、锁几分钟、多大尺寸）、**原样错误串**（用户搜得到）、
   **根因与修法的因果**（为什么必须这样，否则下次照抄会错）。
3. **写 description**：中文；覆盖同义的多种说法（正式/口语/缩写）；带上"即使对方没说 X，只要在做 Y 也应加载"
   这类扩展；**同时写清不适用**（近邻负例是最有效的防误触发手段）。有语言/场景门槛（如"仅中文场景"）
   必须写进 description，否则英文用户会拿到一份读不懂的技能。
4. **写正文**：结构上靠这几样把"能读懂"变成"能执行"——编号层级（一/二/三 + 子编号，方便互相引用）、
   开工前的**快速选择表**（我卡在哪 → 看哪一节）、**决策表**（选项 → 什么情况选它）、每类坑写成
   **判定 / 修复 / 验证**三段、末尾**交付前自查清单**（可打勾）。正文超过 ~500 行就该往 references 拆。
5. **写 evals**：`evals/evals.json`。分两类——**客观类**（打包成功、字段存在、版本号一致、图标尺寸齐）
   写可脚本校验的判据；**主观类**（设计好不好看、文档清不清楚）写评价维度，别硬造断言。
   每条 eval 给一个能读懂的名字，别叫 eval-0。
6. **配模板脚本**：如果评测里发现每次都在重写同一段脚本（打包、生成、校验），那就是该进 `scripts/` 的信号——
   写一次，技能里指明"复制后改顶部几个变量"。
7. **落库与部署**：写进技能库（本机是 `my-skills` 仓库，见 `references/skill-library.md`），
   升 version，并在支持 skills 的各个 agent 目录里部署（链接或复制）。部署后**在一个全新会话里试一次**，
   确认描述能被触发——本机自测通过 ≠ 别人能触发。

## 四、评测流程

**有/无对比**是唯一能说明"技能到底起了作用"的办法：

- **with-skill**：把技能路径给执行者，任务照原样下发；产出存 `.../with_skill/outputs/`
- **baseline**：新建技能用"不给技能"，改进已有技能用"给旧版本快照"（改之前先 `cp -r` 一份快照，
  否则旧版本被覆盖后没法对比）
- 两个 run **同一轮一起下发**，别先跑完一个再补另一个（时间差会让环境因素混进来）
- **保留原始证据**：每次运行的启动命令、stdout/stderr、退出码都落盘成文件；结论要能从证据复算出来
- **评分要严**：客观判据用脚本核（能跑就别眼看），主观部分让独立评审读产出再评；
  "部分完成"要如实扣分——宽松打分会把实现缺陷洗掉，下一轮改稿就失去了方向
- **给用户看产出，而不是只给分数**：把每个用例的产出、上一轮产出、得分、反馈框放在一个页面里让用户过一遍；
  用户的具体抱怨比总分有用得多

**改稿时的三个抓手**（按优先级）：用户抱怨的点 → 一直失败/一直通过的（非区分性）断言 → 时间与令牌消耗异常的用例。
改稿要**从反馈里泛化**，别为某一个用例打补丁；发现评测脚本本身写错了（判据错了、路径错了），
先修评测再改技能，否则会朝错误方向优化。

## 五、优化「技能描述」的触发率

描述决定技能会不会被调用，值得单独跑一轮实验：

1. 造 20 条评测查询：10 条**应该触发**（同一意图的不同说法：正式/口语/带错别字/不说技能名）、
   10 条**不应触发**且**故意贴近**（共享关键词但其实是另一件事）。明显无关的负例测不出任何东西。
2. 查询要**够复杂**：一两句话的简单任务模型自己就能干，不会去查技能，用它测触发率会得到假阴性。
3. 跑一轮自动化：每条查询重复多次统计触发率，按 60/40 分训练集与留出集，只按**留出集**挑最优描述
   （按训练集挑会过拟合）。本机的跑法与 Windows 必须打的三处补丁见 `references/harness-windows.md`。
4. 把最优描述替换回 frontmatter，把前后对比和分数报给用户。

## 六、本机（Windows + 多端）避坑

- 触发评测工具在 Windows 上**开箱即失败**三处：`claude` 实际是 `claude.CMD`（必须 `cmd.exe /c` 包一层，
  否则 `WinError 2`）、管道不能用 `select` 读（`WinError 10038`，改成后台线程读行 + 队列）、
  触发判定写成了老版命令文件格式（新版原生技能传的是纯技能名，两种都要认）。细节与补丁见
  `references/harness-windows.md`。
- 技能会同时装在多个 agent 目录（Claude Code 的 `.claude/skills/<name>/SKILL.md`、pi 的
  `.pi/agent/skills/<name>/`）。**改完只更新一处，另一处就是旧的**——版本号对不上时先查这个。
- 技能库用**软链接**铺到各端，改动会立刻生效，但也意味着"实验性改动"会直接影响日常会话；
  破坏性改动前先复制快照。

## 七、交付前自查

- [ ] `description` 里有触发场景 + 不适用场景（近邻负例），且不含正文才该说的细节
- [ ] 每个数字/字段/错误串都能追溯到来源（文件行号、命令、输出）
- [ ] 推断与实测分开标注；没有"要注意"这类无判据的话
- [ ] 正文有编号层级、快速选择表、判定/修复/验证三段、交付前自查清单
- [ ] 参考资料按主题拆分，SKILL.md 里给了"什么时候读哪个"的指路
- [ ] evals 分客观/主观，客观判据可脚本校验；有/无基线都跑过并留存证据
- [ ] 至少一条真实失败过的坑被写成"判定/修复/验证"（只有成功经验说明还没提炼透）
- [ ] version 已升，且各端部署目录里的版本一致
